# 阶段 1：LLM API 与 Tool Calling

> 第 1 题保留用户自己写的原文。第 2–4 题是用户在对话里作答、经过追问后，由 AI 按对话内容整理的（2026-11-04，用户同意）。
> 练习代码在 `practice/01-tool-calling/`，作业说明见该目录的 `README.md`。

## 理解检查

### 1. 一个 30 轮的对话，第 30 轮的成本大约是第 1 轮的多少倍？这对 agent 设计意味着什么？

**用户原答**：

> 单独看第30轮，会分为缓存命中token和当前输入token+输出token这3部分计费。总共30轮，就是30轮以上计费，其中每一轮的输入与输出，会进入到下一轮的缓存命中里去。
> 工具调用的输出，会作为输入返回给LLM
>
> 按照你的假设，一个是n*(n-1)*0.5倍，一个是线性的1:1倍。
>
> 5000token不论计费额度，但论计费次数是21次。如果有十几个，那么这十几个输出都会被反复计费，而且污染上下文，压缩有效输出token的注意力。然后我能想到的就是仅对关键输出提交？比如说报错，成功之类的。

**批改后的要点**：

- 倍数：模型是无状态的，第 30 轮的输入包含前面所有轮次的内容，单轮成本约为第 1 轮的 30 倍；30 轮累计约 1 + 2 + … + 30 = 465 倍。
- 意味着：模型说过的每一句话、每一次工具输出，都会在之后的每次请求里作为输入被重复计费，还会稀释注意力。对策：
  - 截断大段输出：mini-swe-agent 超过 1 万字符时保留头尾各 5000；opencode 的 `tool-output.ts` 超过 2000 行或 50KB 时截断，全文存盘，并告诉模型文件路径。
  - 缓存：前缀不变才能命中，所以历史只能追加、不能改写。

### 2. 原生 tool calling 相对文本解析，好处和代价各是什么？为什么 mini-swe-agent 还保留文本解析的版本？

**好处**（都有作业 3、4 的实验作证）：

- **格式由训练和 API 保证**：不需要 prompt 约定格式、不需要正则、不需要显式的 `Final Answer` 标记。文本方式下，模型在复述过程时又写了一遍 Action，代码就多执行了一次工具（作业 3 A 组）。
- **不需要靠 `stop` 防止编造**：文本方式不加 `stop` 时，模型编出了"12°C、北风 3 级"，这行假数据留在历史里，后来被它当成"之前的查询结果"（作业 3 A 组）。
- **信息来源清楚**：`role: "tool"` 加 `tool_call_id`。文本方式只能把工具结果冒充成用户的话，模型真的以为是"用户贴出来的"。这还带来注入风险：工具读到的内容（网页、MCP、skill）会被当成用户的指令。
- **可以并行调用，用 id 配对**：作业 4 里模型一步就发起了两个调用，一共 2 步；作业 3 要 3 步。文本方式为了降低风险，通常规定一次只能有一个 Action（mini-swe-agent 也要求"恰好一个"，`actions_text.py:25`）。想要多个，就得在文本里重新发明 id。
- **结束可以是隐式的**：没有 `tool_calls` 就是结束，因为结构由 API 保证。文本方式需要显式标记，才能区分"已经结束"和"格式写坏了"。
- **服务器会检查配对**：漏传一个结果，或者 tool 消息前面没有对应的调用，都会直接返回 400。

**代价**：

- **失去对格式的控制权**：工具定义被厂商的模板渲染进 prompt（带上一个工具，`prompt_tokens` 从 11 涨到 309），你看不见也改不了。文本方式同样要花 token，但措辞可以自己压缩。（用户最初写的是"文本更简洁"，后来修正为这一条。）
- **依赖模型和 API 都支持**，而且各家格式不同：`arguments` 是字符串还是对象、有没有 `is_error`、id 的格式规则、思考内容的回传规则……都要写转换器去适配。
- `arguments` 仍然可能不是合法的 JSON，需要自己处理。

**为什么保留文本版**：

- **兼容性和解耦**：不支持 tool calling 的模型或接口（本地模型、只有续写接口的服务）也能用，换了模型，agent 照样能跑。
- **研究上的可比性**：mini-swe-agent 1.0 和最初的 SWE-agent 用的都是文本方式（`actions_text.py` 第 2–3 行）。保留它，实验结果才能和过去的论文做对比。

### 3. 工具报错时，应该抛异常终止，还是把错误作为结果回传给模型？

判断标准：**模型能不能针对这个错误采取行动。**

- **能 → 作为工具结果回传**，让模型决定下一步：格式错误（作业 3 用故障注入验证过，告诉它格式不对，它下一步就自己改正了）、参数不合法、查不到数据、工具自身遇到的网络错误（比如网页抓取失败）。
- **不能 → 交给程序处理**（重试、终止，或者问用户），不放进上下文：调用模型 API 时的网络错误、401、预算用完、用户中断、harness 自己的 bug。
- **回传的内容要克制、要有用**：大段错误（比如 C++ 的编译报错）不要整段塞进上下文。先回传摘要，模型需要时再用工具去读详细内容。这是用户自己提出的，和 opencode `tool-output.ts`"截断 + 存盘 + 告诉路径"的做法一致。错误信息最好能指出下一步，比如 opencode 的 read 工具找不到文件时，会给出"你是不是想找这几个"（`read.ts` 第 152–170 行）。
- 不管成功还是失败，**每个调用都必须有一条结果**，否则下一次请求返回 400。

### 4. 模型一次请求并行调用了 3 个工具，其中 1 个失败了，你回传什么？

- **3 条结果都回传**，各带自己的 `tool_call_id`，失败的那一条写明错误。
- **`tool_call_id` 一定拿得到**：它在外层 JSON 里，`res.json()` 时就已经解析出来了。`JSON.parse` 会失败的只是 `arguments` 那一层，所以就算参数是乱码，也能带着正确的 id 回传错误，不会触发 400。（用户最初以为会拿不到 id。）
- **实现**：在每个调用内部用 try/catch，把异常转成一条错误结果，这样 `Promise.all` 就不会因为其中一个失败而整体失败（也可以用 `Promise.allSettled`）。作业 4 用故障注入验证过：程序没有崩溃，模型下一步只重新发起了出错的那一个调用。
- **怎么标记"这是一个错误"**：Anthropic 有 `is_error: true`；OpenAI 格式（DeepSeek 用的就是这个）没有这个字段，只能写在文字里，比如加一个"错误："前缀。对模型来说两者区别不大，但**自己的内部格式一定要保留结构化的 `isError`**：界面显示、统计连续失败次数、决定是否重试、阶段 17 的评估，都要用到它。发给 OpenAI 格式时，再转成文字。opencode 内部用的是 `resultType: "error"`，转成 OpenAI 格式时变成文本（`protocols/shared.ts` 第 271 行）。

## 实验记录

- **模型是无状态的**：不带历史，模型就记不住暗号；8 轮对话里，输入从 32 涨到 429 个 token（个人电脑上的实验）。
- **工具定义会被渲染进 prompt**：同一个问题，带上一个工具，`prompt_tokens` 从 11 涨到 309。
- **一次 API 调用就是一个 HTTP POST**：`demo_raw_http.ts` 用 TLS socket 手写请求，能看到原始文本和 chunked 编码。fetch 的两次 await：普通请求的响应头 216ms 就到了，正文等了 35 秒（`demo_await_timing.ts`）。fetch 遇到 4xx / 5xx 不会抛异常；503（服务繁忙）值得重试，401 不值得。
- **DeepSeek 的模型**（2026-11，`GET /models`）：`deepseek-flash`（V4.1-Flash）、`deepseek-v4-pro`。`deepseek-chat` 是旧名字，看起来对应 flash 的非思考模式。同一个问题的输入 token：chat 11，flash 35，pro 88。
- **`max_tokens` 同时包含思考和回答**：设成 5 时，5 个 token 全部用在了思考上，`content` 为空，`finish_reason` 是 `length`。
- **模型不知道今天是几号**：它以为是 2026-05-07，而响应里的 `created` 时间戳是 2026-11-03。没有 system 消息时，它自称"OpenAI 的 ChatGPT"，被追问后又改口。在 system 消息里写上身份和日期后，两个问题都答对了，被追问也不再改口。但注入的时间只是程序启动时的快照；每一轮都去更新 system 消息，又会破坏前缀缓存（这个矛盾留到阶段 4）。
- **模型记不住自己说过的话**：不把它的回答放回历史，它每一轮都把所有问题重新回答一遍，还很笃定地说"只推荐过《三体》"。很多看起来是模型的错误，其实是 harness 给错了上下文。
- **DeepSeek 的缓存命中，以 128 个 token 为单位。**
- **怪 token**：`canSn't`、`IOne`，两次都出现在 "can I" 这个位置，可能是服务器端的系统性问题。
- **文本方式的 ReAct**（作业 3）：用 `stop` 做的 A/B 对照见第 2 题。用户要求换一种调用格式时，模型坚持按 system 消息里的约定写（system 的优先级高于用户），回答里却说得好像照做了（迎合）。
- **原生 tool calling**（作业 4）：`arguments` 是一个 JSON 字符串，相当于 JSON 里套着 JSON。工具各要 1 秒时，并行执行用了 1002ms，顺序执行用了 2007ms。
- **`reasoning_content` 的规则**（受控实验，`demo_reasoning_tokens.ts`）：请求带 tools 时，同一轮工具调用之间不回传思考内容，会直接返回 400（"must be passed back"），而且历史里的思考内容都会被计入输入；请求不带 tools 时，会被忽略。作业 2 得出的"总是被忽略"，只在不带 tools 的前提下成立。
- **闭源厂商不给原始的思考过程**：Anthropic、OpenAI、Gemini 只给摘要或空字符串，外加一段不透明、带签名或加密的数据，要原样传回，而且只有生成它的那个模型能读。DeepSeek 则给完整原文。思考内容和其他输出一样：生成时按输出计费一次，之后每次请求作为输入再计费，命中缓存可以降低这部分费用。

## 对 provider 抽象的结论（练习第 5 步要用）

- **内部格式取"最大公倍数"**：文字、思考内容、工具调用（参数统一存成对象）、工具结果（带 `isError`），再加上各家的专属数据（内部代码不读不改，只原样传回给同一个模型）。
- **每一家写一个转换器**，所有的格式差异都关在转换器里。
- **核心里的历史只追加、不删除**，到发送的那一刻才由转换器决定这一家要发什么。mini-swe-agent 在发送前才去掉 `extra` 字段；opencode 用 `toLLMMessages` 在每次请求前现场转换。
